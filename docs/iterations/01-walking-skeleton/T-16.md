# T-16: Build the image and deploy to staging on merge

(Revised for CR-001, 2026-11-11.) Rewritten for DigitalOcean App Platform. Was ECR, ECS task
definitions and OIDC to AWS. Now: one linux/amd64 image in DigitalOcean Container Registry, the App
Platform spec rendered and applied with `doctl`, migrations as the `PRE_DEPLOY` job (ADR-019 as
amended, C12; ADR-022). The ARM64 build risk (old R7) is gone because App Platform runs amd64.

**Tier:** B (follows architecture 20.2 as amended step by step; infrastructure exists from T-15)
**Links:** Architecture sections 20.2, 20.3, 22 (uptime, heartbeat); ADR-017 (roll back by redeploying
the previous image); ADR-019; NFR-042 (uptime measured outside our hosting); NFR-012 (heartbeat).
**Depends on:** T-02 (CI must pass first), T-15 (registry, app, secrets in the GitHub environment).
Owner prerequisites: Better Stack and Healthchecks.io accounts (free), a scoped DigitalOcean API token
in the GitHub `staging` environment.

## Why
Every merge to `main` should reach staging by itself, with migrations applied first and a smoke test
after, so the owner always tests the latest approved code, and a bad release can be undone in minutes.

## What to build (decisions already made)
**`deploy-staging.yml`**: trigger `workflow_run` of CI completed successfully on `main` (nothing
deploys if CI is red). GitHub environment `staging`. Concurrency group `deploy-staging` (one at a time,
no cancelling a running deploy). Steps:
1. Install `doctl`, authenticate with the scoped token from the environment (no other cloud access).
2. Build **one** image for `linux/amd64` with buildx and the GitHub Actions cache, tag with the full
   commit SHA, push to `registry.digitalocean.com/<registry>/backstagehq:<sha>`. Never tag `latest`.
3. `render_app_spec.py`: read `infra/do/app.staging.yaml`, set the image tag and `GIT_SHA`, fill each
   `type: SECRET` value from the matching environment variable, refuse to run if any is missing, write
   the result to a temporary file outside the workspace, and print nothing secret (every value is
   registered with `::add-mask::` first). The rendered file is never uploaded as an artifact.
4. `doctl apps update $APP_ID --spec <rendered> --wait`. The `PRE_DEPLOY` job runs migrations first; if
   it fails, App Platform keeps the old version serving and the step fails (ADR-017 expand/contract
   makes this safe). If the new containers fail their health check, the deployment fails and the old
   version keeps serving.
5. `smoke_test.py https://staging.<domain>`: `/health/live` 200; `/health/ready` 200 and its `commit`
   equals the deployed SHA (retries for up to 3 minutes); `/signin` 200 and contains "Sign up or sign
   in" and no phone field; `/admin/` 404; response headers include HSTS and a CSP. Fail otherwise.
6. Registry housekeeping: delete tags older than the newest 3 (never the one just deployed) and start
   garbage collection weekly, to stay inside the free Starter tier.
7. Job summary: SHA, image tag, deployment ID and result, smoke result.

**`rollback-staging.yml`**: manual dispatch with `image_tag`; renders the spec with that tag and
applies it the same way (the `PRE_DEPLOY` migrate step finds nothing to apply on the newer schema; no
migration runs backwards, ADR-017); then runs the smoke test expecting that SHA.

**`release-tag.yml`**: unchanged from the approved plan: requires the latest `ci` and `ac-trace` runs on
`main` to be green, runs `record_migration_state.py` (latest applied migration per app from
`showmigrations --plan`) into `app/migrations-at-release.json`, commits it, pushes tag
`release/iteration-NN`.

**Outside checks (the owner creates the accounts; this ticket records the configuration in
`app/README.md`):**
- Better Stack uptime monitor on `https://staging.<domain>/health/ready` every 3 minutes (free tier),
  alerts by email. No sleep window: staging runs all the time (App Platform cannot scale to zero and
  the saving would be small).
- Healthchecks.io check for the worker heartbeat (T-08), period 5 minutes, grace 20 minutes; its URL is
  the `HEARTBEAT_URL` secret.

## Carry-over from the T-01 review (added 2026-11-11)
Found by the `reviewer` on T-01 and deferred to this ticket (see `log.md`, T-01 entry). They fit
the files already listed above. They add no new decision.
- **Health check must not be redirected or refused (major).** App Platform's own health check calls
  `/health/live` inside the platform. It may arrive over plain HTTP without `X-Forwarded-Proto`, or
  with the container's IP as the `Host` header. Then `SECURE_SSL_REDIRECT` answers 301 and
  `ALLOWED_HOSTS` answers 400 (DisallowedHost), and every deploy would fail its health check. Fix in
  `production.py`:
  - add `SECURE_REDIRECT_EXEMPT = [r"^health/"]`;
  - confirm which `Host` the probe sends, then either allow it or answer `/health/*` before the
    host check.
  Since T-01, `staging.py` only does `from .production import *`, so change `production.py` only.
  Prove it with the first real deploy (the health check passes) and a unit test that `/health/live`
  over plain HTTP with an unknown host returns 200 under production settings.
- **Runtime user must not own the code.** Remove `chown -R bhq /app` from `app/Dockerfile`. Keep
  `/app` owned by root and readable by `bhq`. Only paths that must be written at runtime, if any,
  belong to `bhq`.
- **Pin the uv image by digest.** It is `ghcr.io/astral-sh/uv:0.10.11` today, pinned by tag only.
  Use `ghcr.io/astral-sh/uv:<version>@sha256:<real digest>`.

## Acceptance criteria
- Given a merge to `main` with green CI, when the workflow runs, then within about 15 minutes staging
  serves the new SHA on `/health/ready`, and the job summary shows each step's result.
- Given CI failed on `main`, when it finishes, then no deploy starts.
- Given a migration that fails, when the workflow runs, then the new version never takes traffic, the
  workflow fails, and the previous SHA is still served.
- Given a new image whose web container fails its health check, when deployed, then the deployment fails
  and the previous SHA is still served.
- Given `rollback-staging` with the previous tag, when run, then staging serves that SHA again and the
  smoke test passes.
- Given a deploy run's log, when searched for any secret value, then none appears.
- Given `release-tag` for iteration 01 with green checks, when run, then tag `release/iteration-01` exists
  and `app/migrations-at-release.json` lists each app's latest migration.

  failing migration deployed to a temporary copy of the app spec (`bhq-staging-test`, deleted after)
  showing the old version still served; one rollback run.
