# T-16: Build the image and deploy to staging on merge

**Tier:** B (follows architecture 20.2 step by step; infrastructure exists from T-15)
**Links:** Architecture sections 20.2, 20.3, 22 (uptime, heartbeat); ADR-017 (roll back by redeploying
the previous image); ADR-019; NFR-042 (uptime measured outside our hosting); NFR-012 (heartbeat).
**Depends on:** T-02 (CI must pass first), T-15 (ECR, ECS, OIDC role). Owner prerequisites:
Healthchecks.io and Better Stack (or similar) accounts.

## Why
Every merge to `main` should reach staging by itself, with migrations applied first and a smoke test
after, so the owner always tests the latest approved code, and a bad release can be undone in minutes.

## Files to touch
- `.github/workflows/deploy-staging.yml`
- `.github/workflows/rollback-staging.yml` (manual, input: image tag)
- `.github/workflows/release-tag.yml` (manual: tags `release/iteration-NN` after the iteration's review
  and AC-traceability pass; writes `app/migrations-at-release.json` used by T-02's round trip)
- `app/scripts/ci/smoke_test.py`, `app/scripts/ci/record_migration_state.py`
- `app/scripts/ci/tests/test_smoke_test.py`, `test_record_migration_state.py`
- `app/Dockerfile` (only if a change is needed for ARM64 builds; keep T-01's structure)
- `app/README.md` (section "Deploying and rolling back", in plain steps)

## What to build (decisions already made)
**`deploy-staging.yml`** — trigger: `workflow_run` of CI completed successfully on `main` (so nothing
deploys if CI is red). GitHub environment `staging`. Concurrency group `deploy-staging` (one at a time,
no cancel of a running deploy). Steps:
1. OIDC to AWS with the T-15 deploy role (no stored keys).
2. Build **one** image for `linux/arm64` (use an ARM runner if available on the plan, else buildx with
   QEMU and the GitHub Actions cache), tag with the full commit SHA, push to ECR. Never tag `latest`.
3. Register new task-definition revisions for `web`, `worker` and `migrate` pointing at that tag with
   `GIT_SHA` set.
4. Run the `migrate` task with `aws ecs run-task`, wait for it to stop, fail the workflow if its exit
   code is not 0 (the old version keeps running; ADR-017 expand/contract makes this safe).
5. `aws ecs update-service` for `web` and `worker`; `aws ecs wait services-stable` (timeout 15 min). ECS's
   circuit breaker rolls back automatically if the new tasks fail health checks.
6. `smoke_test.py https://staging.<domain>`: `/health/live` 200; `/health/ready` 200 and its `commit`
   equals the deployed SHA (retries for up to 3 minutes); `/signin` 200 and contains "Sign up or sign
   in"; `/admin/` 404; response headers include HSTS and a CSP. Fail the workflow otherwise.
7. Write a job summary: SHA, image tag, migration task result, smoke result.

**`rollback-staging.yml`** — manual dispatch with `image_tag`: re-registers task definitions with that
tag and updates both services (no migrations are run backwards; ADR-017 says the previous code works on
the newer schema). Then runs the smoke test (expecting the rolled-back SHA).

**`release-tag.yml`** — manual dispatch with the iteration number: requires the latest `ci` and
`ac-trace` runs on `main` to be green, runs `record_migration_state.py` (writes the latest applied
migration per app, from `showmigrations --plan`, to `app/migrations-at-release.json`), commits it, and
pushes tag `release/iteration-NN`.

**Outside checks (owner sets up the accounts; this ticket records the configuration in `app/README.md`):**
- Uptime monitor (Better Stack or similar, outside AWS) on `https://staging.<domain>/health/ready` every
  minute; for staging, alerts by email only and paused during the 23:00–08:00 IST sleep window (T-15).
- Healthchecks.io check for the worker heartbeat (T-08), period 5 minutes, grace 20 minutes, same
  sleep-window schedule; URL stored in the `heartbeat_url` secret.

## Acceptance criteria
- Given a merge to `main` with green CI, when the workflow runs, then within about 15 minutes staging
  serves the new SHA on `/health/ready`, and the job summary shows each step's result.
- Given CI failed on `main`, when it finishes, then no deploy starts.
- Given a migration task that exits non-zero, when the workflow runs, then services are not updated and
  the workflow fails, with the previous version still serving.
- Given a new image that fails its health check, when deployed, then ECS rolls back and the workflow
  fails at the stability or smoke step.
- Given `rollback-staging` with the previous tag, when run, then staging serves that SHA again and the
  smoke test passes.
- Given `release-tag` for iteration 01 with green checks, when run, then tag `release/iteration-01` exists
  and `app/migrations-at-release.json` lists each app's latest migration.

## Tests that prove it
- `test_smoke_test.py::test_passes_on_expected_sha_and_headers` (unit, HTTP mocked).
- `test_smoke_test.py::test_fails_on_wrong_sha_after_retries` (unit).
- `test_smoke_test.py::test_fails_when_admin_reachable_or_hsts_missing` (unit).
- `test_record_migration_state.py::test_writes_latest_applied_migration_per_app` (unit, sample
  `showmigrations --plan` output).
- Manual proof recorded in `log.md`: link to one successful deploy run, one run where a deliberately
  failing migration on a throwaway branch merged to a test branch stops the deploy (or a dry run against
  a `staging-test` service), and one rollback run.

## Out of scope
- Production deploys with manual approval and a pre-migration snapshot (iteration 14), the nightly
  Playwright run against staging (T-14 runs e2e in CI; against staging later), CloudWatch alarms
  (iteration 6), blue/green deploys (not planned).
