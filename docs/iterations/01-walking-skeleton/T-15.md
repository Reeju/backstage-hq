# T-15: Staging on the low-cost V0 setup, in Terraform

(Revised for CR-001, 2026-11-11.) Rewritten. Was "Staging infrastructure in Terraform" on AWS ECS, RDS,
ALB and WAF in Mumbai. Now: DigitalOcean Bangalore for the app and database, AWS Mumbai for the KMS
key, SES and Terraform state, Cloudflare for DNS (ADR-022, ADR-023). Everything is in personal
accounts, because staging only ever holds dummy data (V0).

**Tier:** A (database exposure, IAM policies, KMS key policies and stored credentials are security
decisions)
**Links:** ADR-021, ADR-022 (as the V0 setup), ADR-005 (as amended, C7), ADR-019 (as amended, C12),
ADR-023; NFR-043 (in part: point-in-time restore on staging), NFR-048 groundwork (database logging per
spike Q-H1); architecture sections 3A, 12, 19, 23; comparison §5.1.
**Depends on:** T-04 (`db_bootstrap_roles`), T-17 spike **Q-H1 answered "yes"** (DigitalOcean fits).
**Gate:** owner accounts from plan section 11 (DigitalOcean, AWS, Cloudflare with the domain, GitHub).

## Why
Staging is where the owner tests every iteration (playbook stage 7). It must be rebuilt from code
(NFR-043's 8-hour recovery depends on it), cost about $27 a month, be locked down the way production
will be, and use the same modules production will use in V1, so production is "the same code with
different variables".

## What to build (decisions already made)
- **Providers:** Terraform >= 1.10; `digitalocean`, `aws`, `cloudflare` providers pinned. Region
  `blr1` (DigitalOcean) and `ap-south-1` (AWS). All resources tagged or named `bhq-staging`.
- **DigitalOcean project** `bhq-staging` holding everything below.
- **Database** (`do_database`): Managed PostgreSQL 17, `db-s-1vcpu-1gb`, single node, `blr1`; database
  `bhq`; **trusted sources** = the staging app only, plus `operator_cidrs` (variable, default empty)
  for the one-off role bootstrap. Database settings as recorded by spike Q-H1: statement logging off
  (`log_statement=none`, `log_min_duration_statement=-1`) and, if the provider allows them,
  `log_parameter_max_length=0` and `log_parameter_max_length_on_error=0` (architecture 16A.6).
  Maintenance window at night IST. Point-in-time restore is built in (7 days). Deletion is protected by
  a `prevent_destroy` lifecycle rule.
- **Container registry:** DigitalOcean Container Registry, Starter tier (free), repository
  `backstagehq`.
- **App** (`do_app`): a `digitalocean_app` created once from a minimal placeholder spec (a public
  "hello" image) with `lifecycle { ignore_changes = [spec] }`; from then on T-16's workflow owns the
  spec. Outputs the app ID and default ingress. `infra/do/app.staging.yaml` holds the real spec
  template: region `blr`; service `web` (`apps-s-1vcpu-0.5gb`, port 8000, health check `/health/live`,
  `gunicorn` command); worker `worker` (same size, `manage.py run_worker`); job `migrate` (`PRE_DEPLOY`,
  `manage.py migrate --database migrator`); image from the registry with tag `${IMAGE_TAG}`; domain
  `staging.<domain>`; alerts on deployment failure, domain failure, CPU and memory above 80%, restarts;
  environment variables listed by name with `type: SECRET` where secret, values filled only at deploy
  time.
- **KMS** (`aws_keys`): one symmetric key `bhq-staging-data` with alias, rotation on, and a key policy
  that allows `GenerateDataKey` and `Decrypt` only to the two app users and **only when** the
  encryption context has key `workspace_id` or `scope` (condition `kms:EncryptionContextKeys`); the
  operator role may administer but not use it; nobody may `ScheduleKeyDeletion` without the account
  root. (`tokens` key: iteration 5.)
- **SES** (`aws_email`): domain identity with Easy DKIM, custom MAIL FROM, a configuration set; the
  account stays in the **sandbox**, so it only delivers to verified addresses: this is the staging
  allow-list (CR-001 C). The owner's test addresses are verified by the operator (recorded).
- **App identities** (`aws_app_identities`): IAM users `bhq-staging-web` (KMS `data` use only) and
  `bhq-staging-worker` (KMS `data` use; `ses:SendRawEmail` from the staging identity and configuration
  set only). Access keys are **not** created by Terraform (they would land in state); the operator
  creates them with the CLI and stores them only in the GitHub `staging` environment (T-16 puts them in
  the app as encrypted secrets). Rotation every 90 days is in `infra/README.md`.
- **Budgets** (`aws_budget`): AWS Budget at US$5 a month with email alerts at 80% and 100%. A
  DigitalOcean billing alert at US$35 (set by the operator in the console, recorded; no Terraform
  resource).
- **DNS** (`cloudflare_dns`): `staging.<domain>` CNAME to the app's default ingress (DNS only, not
  proxied, in V0); SES DKIM CNAMEs; MAIL FROM MX and SPF TXT; DMARC TXT `p=quarantine` with a reporting
  address.
- **No edge rate rule, no WAF, no load balancer**: the edge rule is deferred in the validation phase
  (PRD 4.5); App Platform terminates TLS.

**Operator steps (each recorded in `log.md` with the command and result):**
1. `terraform apply` in `infra/bootstrap`, then in `infra/envs/staging`.
2. Add your IP to `operator_cidrs`, apply, run `manage.py db_bootstrap_roles` with
   `DATABASE_ADMIN_URL` = the `doadmin` connection string, run it a second time (no changes), remove the
   IP, apply again.
3. Create the two IAM access keys and put them, with the database role passwords, `DJANGO_SECRET_KEY`,
   `OTP_PEPPER`, `SENTRY_DSN` and `HEARTBEAT_URL`, into the GitHub `staging` environment secrets.
4. Verify the owner's test email addresses in SES.

## Acceptance criteria
- Given a clean checkout, when `infra-check.yml` runs, then fmt, validate, tflint and checkov pass, and
  any accepted checkov finding is listed in `infra/README.md` with a reason.
- Given an apply, when finished, then the database is not reachable from the internet: a `psql`
  connection from a machine outside the trusted sources fails.
- Given `db_bootstrap_roles` run twice as `doadmin`, when inspected, then all roles exist, none has
  `rolbypassrls` or `rolsuper`, and the second run changed nothing.
- Given the web IAM user, when `aws iam simulate-principal-policy` (or the KMS policy simulator) is run,
  then `kms:Decrypt` with a `workspace_id` context is allowed and without it denied, and
  `ses:SendRawEmail` and `kms:ScheduleKeyDeletion` are denied; given the worker user, then sending from
  the staging identity is allowed and from any other identity denied.
- Given the database settings, when `SHOW` is run for the logging parameters, then they match the
  values Q-H1 recorded (statement logging off at least).
- Given the AWS account, when budgets are listed, then the US$5 budget with both alerts exists; the
  DigitalOcean billing alert is recorded.
- Given the DigitalOcean invoice preview after one full day, when read, then the projected month is at
  most about US$27 for the project.

## Tests that prove it
