# T-15: Staging infrastructure in Terraform

**Tier:** A (IAM, KMS key policies, network exposure and database roles are security decisions)
**Links:** ADR-002 (AWS Mumbai, lean posture S4), ADR-005 (KMS keys), ADR-019 (environments, OIDC),
NFR-042, NFR-043 (in part: point-in-time restore on staging), NFR-028 (WAF rate rule), NFR-048
groundwork (database log parameters); architecture sections 2, 12, 19, 22, 23, 24.1.
**Depends on:** T-04 (`db_bootstrap_roles` command). **Gate:** the owner's decision on CR-001 (plan
section 10) and owner prerequisites: AWS Organization with a staging account, a domain with a Route 53
hosted zone, MSG91 and Sentry secrets available.

## Why
Staging is where the owner tests every iteration (playbook stage 7). It must be rebuilt from code
(NFR-043's 8-hour recovery depends on it), cost little, and be locked down like production will be.

## Files to touch
- `infra/README.md` (plain-language: what exists, how to apply, how to destroy)
- `infra/bootstrap/` (state bucket with versioning and encryption, S3 native state locking; applied once)
- `infra/modules/network/`, `database/`, `keys/`, `app_service/`, `edge/` (ALB, ACM, WAF), `email/`
  (SES identity, DKIM), `ci_oidc/`, `observability/` (log groups, budget)
- `infra/envs/staging/main.tf`, `variables.tf`, `outputs.tf`, `versions.tf`, `staging.tfvars`
- `.github/workflows/infra-plan.yml` (runs `terraform fmt -check`, `validate`, `tflint`, `checkov` and
  `plan` on PRs touching `infra/`; apply stays manual in this iteration)

## What to build (decisions already made)
- **Provider and region:** AWS `ap-south-1`. Terraform >= 1.9, AWS provider pinned. All resources tagged
  `env=staging`, `app=backstagehq`.
- **Network (S4 lean):** one VPC, two AZs; public subnets for Fargate tasks with security groups that
  accept inbound only from the ALB security group; private subnets for RDS with no internet route; **no
  NAT gateway** (tasks reach AWS APIs and providers through public IPs; outbound allowed).
- **Database:** RDS PostgreSQL 17, `db.t4g.micro` for staging, single-AZ, 20 GB gp3, storage encrypted
  with KMS key `rds`, automated backups 7 days with point-in-time restore, deletion protection on,
  `rds.force_ssl=1`, parameter group with `log_parameter_max_length=0` and
  `log_parameter_max_length_on_error=0` (architecture 16A.6), `log_min_duration_statement=1000`. Master
  password managed by RDS in Secrets Manager. Cross-region backup copy is production-only (iteration 14).
- **Keys (ADR-005):** KMS keys `data`, `tokens`, `rds`, single-Region for staging (multi-Region is a
  production requirement for the Hyderabad replica). Key policies: `data` usable for
  `GenerateDataKey`/`Decrypt` by the web and worker task roles, with the condition that
  `kms:EncryptionContext:workspace_id` is present; `tokens` usable by the worker role only (unused until
  iteration 5); no `kms:ScheduleKeyDeletion` for the deploy role.
- **Secrets Manager:** `django_secret_key`, `otp_pepper`, DB passwords for `bhq_migrator`, `bhq_web`,
  `bhq_worker`, `bhq_eraser`, `msg91`, `sentry_dsn`, `heartbeat_url`. Values set by the owner/operator,
  never in Terraform state as plaintext (create the secret shells; values put by CLI).
- **App service:** ECR repository (immutable tags, scan on push, lifecycle keeps 30 images); ECS
  cluster; task definitions `web` (0.25 vCPU / 0.5 GB for staging, ARM64, port 8000, health check
  `/health/live`), `worker` (same image, `manage.py run_worker`), `migrate` (one-off,
  `manage.py migrate --database migrator`), `bootstrap-roles` (one-off, `db_bootstrap_roles` using the RDS
  master secret); services `web` (1 task) and `worker` (1 task) with deployment circuit breaker and
  rollback on. Task roles: web (KMS `data`, read its secrets), worker (KMS `data` and `tokens`, SES
  `SendEmail` from the verified domain, read its secrets), execution role (ECR pull, logs, secrets).
  `GIT_SHA` passed as an environment variable per deploy.
- **Edge:** ALB with HTTPS (ACM certificate for `staging.<domain>`), HTTP redirects to HTTPS, idle timeout
  60 s; target group health check `/health/ready`. AWS WAF on the ALB: AWS managed common rule set, known
  bad inputs, IP reputation list, and a **rate-based rule** of 100 requests per 5 minutes per IP on
  `/signin*` and `/account/second-method*` (NFR-028). Route 53 alias record.
- **Email:** SES domain identity with DKIM and a custom MAIL FROM; sandbox mode stays on; the owner adds
  verified recipient addresses for the demo (risk R2). No receiving rules (decided after Q-V3).
- **CI access:** GitHub OIDC provider and a deploy role trusted only for this repository's `main` branch
  and the `staging` GitHub environment: ECR push, `ecs:RunTask`/`UpdateService`/`DescribeServices`,
  `iam:PassRole` on the task roles only. No long-lived AWS keys anywhere.
- **Observability and cost:** CloudWatch log groups for web, worker, migrate with 30-day retention
  (architecture 18.1); an AWS Budget on the staging account at US$80/month with email alerts at 80% and
  100%; GuardDuty (account-level) on.
- **Staging can sleep:** a scheduled action sets both services to 0 tasks at 23:00 IST and back to 1 at
  08:00 IST (saves Fargate cost; RDS stays up).

## Acceptance criteria
- Given `terraform plan` for `envs/staging` from a clean checkout, when run, then it succeeds with no
  errors, and `checkov` reports no high-severity finding that is not listed in `infra/README.md` with a
  reason.
- Given an apply, when finished, then `https://staging.<domain>/health/live` returns 200 once T-16 has
  deployed an image, and the database is not reachable from the internet (connection from outside the
  VPC times out).
- Given the `bootstrap-roles` task, when run twice, then roles exist and the second run changes nothing.
- Given the deploy role, when it tries any action outside its policy (for example `kms:Decrypt` on
  `data`, or `rds:DeleteDBInstance`), then AWS denies it.
- Given more than 100 requests in 5 minutes from one IP to `/signin`, when sent, then WAF blocks the rest.
- Given the RDS parameter group, when inspected, then both `log_parameter_max_length` settings are 0.
- Given the staging account, when the budget is inspected, then the alert exists.

## Tests that prove it
- `infra-plan.yml` checks on the PR (fmt, validate, tflint, checkov, plan) — static, automated.
- Manual verification recorded in `log.md`, one line each with the command and result:
  `curl` health check; `psql` from a laptop to the RDS endpoint times out; `aws iam simulate-principal-
  policy` for the denied deploy-role actions; a burst of 120 `curl` requests to `/signin` returns 403
  after the limit; `aws rds describe-db-parameters` shows the two zeros.
