# T-06: Action runner and append-only activity log

**Tier:** A (audit integrity, permission enforcement path, PII in undo values)
**Links:** FR-213 AC1 (in part), AC2; NFR-032 (in part), NFR-033 (data kept for export later),
NFR-034 (actor labels); ADR-007, ADR-010; architecture sections 4 (rule 1), 6.5 (`ACTIVITY_LOG`), 15.
**Depends on:** T-05 (policy), T-07 (encryption of sensitive undo values).

## Why
"One door for changes": every write checks permission, makes the change, writes a plain-words log
entry and records how to undo it, all in one database transaction. If the change rolls back, so does
the entry. Nobody, including the owner, can edit or delete the log.

## What to build (decisions already made)
**Table `audit_activitylog`** exactly as architecture 6.5 (`seq` bigint primary key from a sequence,
`workspace_id`, `at`, `actor_kind`, `actor_user_id`, `on_behalf_of_user_id`, `assistant_run_id`
nullable with no FK yet, `action`, `target_type`, `target_id`, `summary`, `undo` jsonb, `visibility`,
`prev_hash`, `entry_hash`). Forced RLS with `EnableWorkspaceRLS`. Index `(workspace_id, seq DESC)`.

**Append-only (ADR-010).** Migration `0002_append_only.py`:
`REVOKE UPDATE, DELETE, TRUNCATE ON audit_activitylog FROM bhq_web, bhq_worker`; a `BEFORE UPDATE OR
DELETE` row trigger and a `BEFORE TRUNCATE` statement trigger that raise an exception unless
`current_user = 'bhq_eraser'` and the operation is `DELETE`. Reverse drops the triggers and restores
the grants.

**Hash chain (15).** On insert, inside the same transaction: take
`pg_advisory_xact_lock(hashtextextended('audit:' || workspace_id::text, 0))`; read the latest
`entry_hash` for the workspace (or 32 zero bytes); get `seq` with `nextval()` first; compute
`entry_hash = SHA-256(canonical JSON of every column except entry_hash, with prev_hash hex)`; insert
once (no update is ever needed). `chain.verify(workspace_id) -> int | None` returns the first broken
`seq` or `None`. Canonical JSON: sorted keys, UTF-8, timestamps in ISO-8601 UTC with microseconds,
UUIDs lower-case.

**Registry and runner (ADR-007).**
- `@action(name, action_type, *, summary, internal=True, creates_workspace=False)` registers a function
  `fn(ctx, **inputs) -> ActionResult(target_type, target_id, before, sensitive_before_keys)`.
  `summary` is a template string or callable that produces plain words ("You added your bank account
  for invoices"), never raw values of sensitive fields.
- `run_action(actor, workspace_id, name, *, context=None, **inputs)`:
  1. opens `workspace_context(workspace_id)` (atomic + RLS setting);
  2. calls `authorize(actor, workspace_id, action_type, context=context)`; `DENY` raises
     `ActionDenied` **after** writing a refusal entry (`action="<name>.refused"`, summary "Refused:
     <reason>") in a separate transaction for that workspace, so refusals are logged even though the
     change is not (architecture 15, security events); `STEP_UP` raises `StepUpRequired` (no entry);
     `QUEUE` raises `QueueRequired` (the queue arrives in iteration 5);
  3. marks the guard as "inside an Action" and calls the function;
  4. encrypts the values in `before` whose keys are in `sensitive_before_keys` with T-07's helper
     (table `audit_activitylog`, column `undo`, row = the log `seq`) and stores the rest as JSON;
  5. writes the log entry with actor labels (`labels.py`: "You" for the owner viewing their own entry;
     "System"; "Assistant for <name>"; "BackstageHQ support"; stored `actor_kind` per 6.5);
  6. returns the result. Any exception rolls back the change and the entry together.
- `creates_workspace=True` lets `workspaces.create_workspace` run before a membership exists: the
  runner generates the workspace ID, sets the context to it, and authorizes "the actor becomes the
  owner of a new workspace" (allowed only for a `person` actor with no ID collision).
- Security events from outside a workspace request (used by T-10, T-11): `record_security_event(user_id,
  event, summary)` runs a system Action of type `record_security_event` in **each** workspace returned
  by `workspace_ids_for_user(user_id)` where that user is the owner.

**Guard.** `WorkspaceScopedModel.save()`, `.delete()` and the scoped queryset's `update()`/`delete()`
raise `WriteOutsideAction` when `ACTION_GUARD_STRICT` is true (local and test) and no Action is
running. `guard.allow_writes_outside_action()` is a context manager for test factories and data
migrations only (the reviewer rejects it anywhere else).

**Selector.** `audit.selectors.recent_entries(workspace_id, limit=50)` returns entries newest first with
display labels and **no** `undo` content. Used by T-12.

## Acceptance criteria
- Given an Action that changes a record, when it succeeds, then exactly one log entry exists in the
  same workspace, committed in the same transaction (FR-213 AC1, in part).
- Given an Action that raises after making its change, when it runs, then neither the change nor a log
  entry is kept.
- Given `bhq_web` or `bhq_worker`, including when acting for the owner, when an `UPDATE`, `DELETE` or
  `TRUNCATE` on the log is attempted, then the database refuses it (FR-213 AC2).
- Given `bhq_eraser`, when it deletes a workspace's entries, then it succeeds (used only by the later
  deletion job).
- Given 20 entries written concurrently by 4 threads in one workspace, when `chain.verify` runs, then it
  returns `None`; given one entry's `summary` altered by a superuser in the test, then it returns that
  `seq`.
- Given an Action whose `authorize` result is `DENY`, when it runs, then the change is not made, a
  refusal entry is logged, and `ActionDenied` is raised.
- Given strict mode, when a scoped model is saved outside an Action, then `WriteOutsideAction` is raised.
- Given a sensitive before-value (for example an old bank number), when stored in `undo`, then the raw
  column does not contain the plaintext.
- Given two workspaces, when log entries are read in A's context, then none of B's appear.
