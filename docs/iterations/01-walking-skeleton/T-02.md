# T-02: CI pipeline on every push

**Tier:** B
**Links:** Playbook rule "CI from iteration 1"; architecture section 20.1 and 20.3; ADR-017
(reversible migrations); ADR-019.
**Depends on:** T-01. Owner prerequisite: the repo is pushed to a private GitHub repository with
Actions enabled.

## Why
Builders are AI and the owner cannot read every line, so the pipeline is the main safety net. It must
exist before real code arrives, and every later ticket must pass it.

## Files to touch
- `.github/workflows/ci.yml` (push to any branch, and pull requests)
- `.github/workflows/nightly.yml` (schedule; runs the Playwright suite once T-14 adds it; until then a
  placeholder job that runs `pytest -m e2e` and passes when no tests are collected)
- `.github/dependabot.yml`
- `.gitleaks.toml`
- `app/pyproject.toml` (`[tool.importlinter]` section, coverage settings)
- `app/scripts/ci/migration_roundtrip.py`
- `app/scripts/ci/tests/test_migration_roundtrip.py`

## What to build (decisions already made)
One workflow, `ci.yml`, with these jobs (all must pass for a merge; set branch protection on `main`
to require them, recorded as an owner step in `log.md`):

| Job | Command | Fails when |
|---|---|---|
| `lint` | `uv run ruff check` and `uv run ruff format --check` | any issue |
| `types` | `uv run mypy .` (strict for `bhq.workspaces`, `bhq.files`, `bhq.rules` once they exist; later `payments`, `invoicing`, `outbound`) | any error |
| `tests` | `uv run pytest --cov` against a `postgres:17` service container | any failure; coverage under 90% for the strict modules (`coverage report --include=... --fail-under=90`; skipped for modules that do not exist yet) |
| `contracts` | `uv run lint-imports` | a forbidden import |
| `migrations` | `manage.py makemigrations --check --dry-run`; then `migration_roundtrip.py` | missing migration; a migration with no reverse; round-trip failure |
| `deps` | `uv lock --check`; `uv export --frozen --no-hashes | uvx pip-audit -r /dev/stdin --strict` | lockfile out of date; any known vulnerability (reviewed exceptions only through an ignore list in the repo, each with a reason and expiry date) |
| `security` | `gitleaks` (official action), `semgrep --config p/django --config p/python --error`, `manage.py check --deploy --fail-level WARNING` with `config.settings.staging` and dummy env values | any finding above low |

- **Postgres in CI:** the service container's superuser is used **only** to bootstrap roles (T-04
  adds `manage.py db_bootstrap_roles`); tests must then connect as the non-superuser role from T-04.
  In this ticket, leave a clearly marked step `bootstrap-roles` that T-04 fills in.
- **`migration_roundtrip.py`:** (1) migrate from empty; (2) find the previous release: the newest
  git tag matching `release/*`; if one exists, read its migration state from the file
  `app/migrations-at-release.json` committed with that tag (written by the deploy job, T-16) and
  migrate each app back to that state; if no release exists yet, migrate every app back to `zero`;
  (3) migrate forward again; (4) exit non-zero on any error. A migration whose operation is
  irreversible fails step 2 by design (ADR-017).
- **import-linter:** create the config with one contract now, "`bhq` modules do not import from
  `config`", so the tool runs; later tickets add their contracts (T-07 adds the KMS one, T-13 adds the
  rules one). A contract may only name modules that exist.
- **Dependabot:** weekly for `uv` (directory `/app`), `github-actions`, `docker` (`/app`), and
  `terraform` (`/infra`, once it exists).
- Cache uv downloads between runs. Pin every third-party action to a commit SHA.

## Acceptance criteria
- Given a push to any branch, when CI runs, then all seven jobs run and report separately.
- Given a branch that adds a model field without a migration, when CI runs, then `migrations` fails.
- Given a branch with a `RunPython` migration that has no `reverse_code`, when CI runs, then
  `migrations` fails at the backwards step.
- Given a branch containing a string that looks like an AWS secret key, when CI runs, then
  `security` fails.
- Given a dependency pinned to a version with a known vulnerability, when CI runs, then `deps` fails.
- Given the current skeleton (T-01), when CI runs, then every job passes.

## Tests that prove it
- `app/scripts/ci/tests/test_migration_roundtrip.py::test_roundtrip_from_zero_when_no_release_tag`
  (unit, subprocess calls mocked): issues migrate-to-zero then migrate.
- `app/scripts/ci/tests/test_migration_roundtrip.py::test_roundtrip_to_previous_release_state`
  (unit): with a fake tag and `migrations-at-release.json`, issues per-app migrate commands to those
  names.
- `app/scripts/ci/tests/test_migration_roundtrip.py::test_exits_nonzero_on_failure` (unit).
- Manual proof recorded in `log.md`: links to one red run per failing case above (throwaway branches,
  deleted afterwards) and one green run.
