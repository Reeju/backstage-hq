# T-18: Invite-only access, the waitlist and the staff log

(New for CR-001, 2026-11-11.) Split out of T-10 so each ticket fits one session.

**Tier:** A (it gates who can create an account; it holds personal data outside any workspace)
**Links:** FR-006 AC1, AC2, AC3, AC4; FR-005 AC2; PRD section 4.4 (waitlist) and 4.5; ADR-023;
architecture sections 6.2 (platform tables `INVITE`, `WAITLIST_ENTRY`, `STAFF_EVENT`), 9, 18.1; mockup
**S-01** as amended (invite-only message, "My country is not listed", waitlist form).
**Depends on:** T-10 (`may_request_code` hook, `normalise_email`, the sign-in form), T-06 (append-only
pattern for the log trigger).

## Why
In the validation phase only people the owner invited may create an account, and people from countries
that are not supported yet join a waitlist instead of getting a workspace. The owner must be able to add
or remove an invite without a deploy, and every such change is recorded.

## What to build (decisions already made)
- **`Invite`** (global, no RLS): `id`, `email_lower` (unique, from `normalise_email`), `added_by`
  (staff user, nullable when added by the command's `--by` email that has no user yet), `created_at`,
  `removed_at`. `is_invited(email)` is true for a row with `removed_at IS NULL`.
- **`may_request_code(email)`** (T-10's hook): if `BHQ_INVITE_ONLY` is false → `True` (FR-006 AC4). If
  a user with that email already exists → `True` (existing users are not re-checked). Else
  `is_invited(email)`. When false, the view sends **no email**, creates no code request, and redirects
  to `/signin/invite-only`: "BackstageHQ is invite-only for now", with a link to the waitlist (FR-006
  AC1). The response time and wording do not depend on whether an account exists beyond this rule.
- **Waitlist** (`/waitlist`, also reached from "My country is not listed" on S-01): a form with email and
  country (an ISO country list, any country) and the consent line from the amended S-01, versioned by
  `WAITLIST_CONSENT_VERSION`. Creates or updates one `WaitlistEntry` per email (`email_lower`,
  `country_code`, `consent_version`, `consented_at`, `removal_token_hash`) and **no workspace, user or
  code** (FR-005 AC2). The thanks page says what happens next. The removal token is generated now and
  only its hash stored; the remove link and the 7-day deletion (FR-005 AC5) ship with the first
  waitlist email, later.
- **Staff command** `manage.py invites add <email> --by <staff email>`, `remove <email> --by ...`,
  `list` (masked emails). Add and remove take effect immediately (FR-006 AC3: "within 5 minutes without
  a code change") and each writes one `StaffEvent` (`staff_user_id` or the `--by` value hashed,
  `action` `invite_added` or `invite_removed`, `subject_hash` = HMAC of the email with `OTP_PEPPER`,
  `created_at`). The command refuses to run without `--by`.
- **`StaffEvent`** is append-only: insert and select only for app roles, and a trigger raises on
  `UPDATE` or `DELETE` (same pattern as the activity log, T-06).
- Logs: no email address in plain text in any log line (redaction from T-09 masks it).

## Acceptance criteria
- **FR-006 AC1 (verbatim):** Given the validation phase is on and an email address is not invited, when a
  sign-in code is requested, then no email is sent and the page says "BackstageHQ is invite-only for
  now", with the waitlist.
- **FR-006 AC2 (verbatim):** Given an invited address, when the person signs up, then FR-001 AC1 applies.
- **FR-006 AC3 (verbatim):** Given the owner adds or removes an invited address, when done, then it takes
  effect within 5 minutes without a code change, and the change is in the staff log.
- **FR-006 AC4 (verbatim):** Given the validation phase is switched off, when anyone in a supported
  country signs up, then no invite check is made.
- **FR-005 AC2 (verbatim):** Given a person who chooses "My country is not listed", when they continue,
  then no workspace is created and they can join the waitlist with only their email and country.
- Given an existing user whose invite was later removed, when they sign in, then they can still sign
  in (the invite gates sign-up only).
- Given a `StaffEvent` row, when an `UPDATE` or `DELETE` is attempted as `bhq_web`, then the database
  refuses it.
- Given the RLS meta-test, when it runs, then `accounts_invite`, `accounts_waitlistentry` and
  `audit_staffevent` are listed as known platform tables and contain no `workspace_id` column.
