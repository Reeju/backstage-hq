# T-04: Tenancy: users, workspaces, memberships, database roles and forced RLS

(Revised for CR-001, 2026-11-11.) Changes: the workspace gets `country_code`, `currency` and `timezone`
with no defaults (FR-005, architecture C3); `user.email` becomes the required sign-in identity (C4); no
role has `BYPASSRLS`, so `bhq_crossws` reads through a role-scoped policy and the role bootstrap must run
as a provider admin that is not superuser, as on managed PostgreSQL (C9, ADR-004 as amended).

**Tier:** A (tenancy and row-level security; a mistake here leaks one creator's data to another)
**Links:** NFR-001, NFR-023; FR-005 (workspace fields); ADR-004 (as amended, C9); architecture sections
6.1, 6.2, 8 (URLs), 11.1–11.4.
**Depends on:** T-01. Plan decision D2 approved (`user_workspace_ids` function).

## Why
Every business record belongs to exactly one workspace, and three locks keep workspaces apart: the
app checks membership on every request, the database refuses rows from another workspace (RLS), and
encrypted fields are bound to their workspace (T-07). This ticket builds the first two locks and the
tests that keep them true for every table added later.

## What to build (decisions already made)
**Models (architecture 6.2).**
- `accounts.User` (`AbstractBaseUser`, no password use; `set_unusable_password()` on create): `id`
  UUIDv7, `email` **required** and unique (case-insensitive unique index on `lower(email)`; it is the
  sign-in identity), `phone_e164` unique nullable (only used where phone codes are switched on),
  `display_name`, `is_staff` (default false), `created_at`. `USERNAME_FIELD = "email"`. Global table,
  no RLS.
  Add `django.contrib.auth` to `INSTALLED_APPS` in this ticket (needed for `AbstractBaseUser`).
- `workspaces.Workspace`: `id` UUIDv7, `owner_user_id` FK, `country_code` (2 upper-case letters),
  `currency` (3 upper-case letters), `timezone` (IANA name), **none with a default** (check constraints
  on the two code formats; `timezone` validated with `zoneinfo` in the service), `status` (`active`,
  `deletion_pending`, `deleted`), `created_at`. The values come from the country's rule set at sign-up
  (T-10 passes them in); this ticket does not import `bhq.rules`.
- `workspaces.Membership`: per 6.2 including the v1 rule columns (nullable/defaults), `role_preset`,
  `status`, `invited_by`. Unique `(workspace_id, user_id)`. Partial unique index: exactly one
  `role_preset='owner'` membership per workspace.
- `workspaces.PermissionGrant`: per 6.2 (empty in the MVP; table exists so v1 is not a rebuild).
- Abstract base `WorkspaceScopedModel` (`workspace` FK, `version` int for optimistic locking, UUIDv7
  `id`) with a manager that raises `NoWorkspaceContext` if no workspace context is active (see below).
  Later business models inherit from it.

**Database roles (11.2, as amended C9).** `manage.py db_bootstrap_roles` (idempotent, run with an admin
connection from `DATABASE_ADMIN_URL`; passwords from environment variables) creates:
`bhq_migrator` (owns tables, `NOSUPERUSER NOBYPASSRLS`; `CREATEDB` only where the admin can grant it,
for the test database), `bhq_web` and `bhq_worker` (`LOGIN NOSUPERUSER NOBYPASSRLS`), `bhq_crossws`
(`NOLOGIN NOBYPASSRLS`, owns the cross-workspace functions), `bhq_eraser` (`LOGIN NOBYPASSRLS`, used only
by the later deletion job). **No role gets `BYPASSRLS`.** The admin it runs as has `CREATEROLE` but is
**not** a superuser (that is all DigitalOcean's `doadmin` and other managed hosts give), so the command
must use only what such an admin may do. It grants `bhq_crossws` to `bhq_migrator`
`WITH INHERIT FALSE, SET TRUE` (PostgreSQL 16+), so a migration can hand function ownership to
`bhq_crossws` without `bhq_migrator` inheriting its read policy. It never makes `bhq_web`, `bhq_worker`
or `bhq_eraser` members of `bhq_crossws`. It sets `ALTER DEFAULT PRIVILEGES FOR ROLE bhq_migrator` so new tables grant
`SELECT, INSERT, UPDATE, DELETE` to `bhq_web` and `bhq_worker`. The `vault` schema and break-glass
role come later. Settings: `DATABASES["default"]` is the app role (`bhq_web` for web, `bhq_worker`
for worker), migrations run with `DATABASE_MIGRATOR_URL` (`manage.py migrate --database migrator`).

**RLS (11.1).**
- `rls.py` provides a migration operation `EnableWorkspaceRLS(table, column="workspace_id")` that runs
  `ENABLE` and `FORCE ROW LEVEL SECURITY` and creates policy `workspace_isolation` `FOR ALL USING
  (<column> = NULLIF(current_setting('app.workspace_id', true), '')::uuid) WITH CHECK (same)`, with a
  reverse that drops them. `NULLIF` matters: after a transaction-local setting ends, Postgres returns
  `''`, and `''::uuid` would raise instead of returning no rows.
- Apply it to `workspaces_membership` and `workspaces_permissiongrant` (column `workspace_id`) and to
  `workspaces_workspace` (column `id`).
- A second operation `AllowCrossWorkspaceRead(table)` creates policy `crossws_read FOR SELECT TO
  bhq_crossws USING (true)` and `GRANT SELECT` to `bhq_crossws`, with a reverse. Apply it only to
  `workspaces_membership` (what `user_workspace_ids` reads). Each later cross-workspace function adds it
  for the tables it reads, listed in the ADR-004 appendix.
- `context.py`: `workspace_context(workspace_id)` context manager = `transaction.atomic()` +
  `SELECT set_config('app.workspace_id', %s, true)` (bound parameter; never string formatting, never a
  session-level `SET`) + a `contextvars` marker read by the scoped manager. Nesting with a different
  workspace raises.
- `user_workspace_ids(p_user_id uuid) RETURNS SETOF uuid`: `SECURITY DEFINER`, owned by
  `bhq_crossws` (which reads memberships through `crossws_read`, not by bypassing RLS), `SET search_path = pg_catalog, public`, returns only `workspace_id` of memberships
  with `status='active'`; `REVOKE ALL ... FROM PUBLIC`; `GRANT EXECUTE` to `bhq_web`, `bhq_worker`.
  Exposed in Python as `workspaces.selectors.workspace_ids_for_user(user_id)`.
- Creating a workspace: generate the UUIDv7 in Python, enter `workspace_context(new_id)`, then insert
  the workspace and the owner membership (the `WITH CHECK` passes because the setting matches). No
  special function is needed. Expose `workspaces.services.create_workspace_with_owner(user, *,
  country_code, currency, timezone)` for T-10 (T-06 later wraps it in an Action); all three arguments
  are required keyword arguments.

**App lock (11.1, 8).** `WorkspaceMiddleware` (or a view decorator applied by the URL prefix helper)
for every path under `/w/<uuid:workspace_id>/`: requires a signed-in user (sessions arrive in T-10, so
tests here build requests with `RequestFactory` and set `request.user` directly), opens `workspace_context`, checks an active membership for
`request.user`; if none, or the workspace does not exist, returns **404** (never 403: do not reveal
that a workspace exists), and writes a technical log warning `workspace_access_refused` with user ID
and requested ID (NFR-001 "refused and logged"). Sets `request.workspace` and `request.membership`.

**CI bootstrap as a managed host would run it.** In `ci.yml`'s `bootstrap-roles` step, the service
container's superuser first creates `bhq_admin` (`LOGIN NOSUPERUSER CREATEROLE CREATEDB NOBYPASSRLS`),
and `db_bootstrap_roles` then runs **as `bhq_admin`**. If the command needs superuser, CI fails.

**Tests that keep it true (11.4).**
- `app/bhq/workspaces/testing.py`: `assert_cross_tenant_isolated(make_row)` creates workspaces A and B,
  a row in each, then checks as `bhq_web` that in A's context: ORM `.all()` returns only A's row;
  raw SQL `SELECT` returns only A's row; `UPDATE`/`DELETE` of B's row affect 0 rows; `INSERT` with
  B's `workspace_id` raises. With no context: 0 rows. Later tickets call this for each model.

## Carry-over from the T-01 review (added 2026-11-11)
Found by the `reviewer` on T-01 and deferred to this ticket (see `log.md`, T-01 entry). It adds no
new decision.
- **Local migrations must run as the migrator role.** Since T-01, compose `web` runs
  `manage.py migrate --noinput && manage.py runserver` with the app's own database login.
  Otherwise a fresh database would leave `/health/ready` at 503.
  - When this ticket adds the roles, run local migrations as `bhq_migrator`
    (`migrate --database migrator`), never as `bhq_web`.
  - Preferably make it a one-shot compose `migrate` service, after the role bootstrap, that `web`
    waits for (`depends_on: condition: service_completed_successfully`).
  - `/health/ready` must still return 200 on a fresh clone.

## Acceptance criteria
- Given any table with a `workspace_id` column (plus `workspaces_workspace`), when the meta-test runs,
  then RLS is enabled and forced and the `workspace_isolation` policy exists; a new table without it
  fails the test. Any other policy must be `crossws_read` on a table in the allowed list (today only
  `workspaces_membership`) or `backup_read`; anything else fails. Global tables without `workspace_id`
  must be on a known platform-table list in the test.
- Given two workspaces, when code in A's context reads or writes through the ORM or raw SQL, then
  nothing of B's is returned or changed (NFR-023 foundation).
- Given no workspace context, when a scoped model is queried through the ORM, then
  `NoWorkspaceContext` is raised; when queried by raw SQL as `bhq_web`, then 0 rows return.
- Given the roles used by the app and by tests, when inspected in `pg_roles`, then `rolsuper` and
  `rolbypassrls` are false for `bhq_web`, `bhq_worker`, `bhq_migrator`, `bhq_crossws` and `bhq_eraser`.
- Given `bhq_migrator` outside any workspace context, when it selects from `workspaces_membership`, then
  0 rows return (its `bhq_crossws` membership does not inherit the read policy); and `bhq_web`,
  `bhq_worker` and `bhq_eraser` are not members of `bhq_crossws`.
- Given CI, when `db_bootstrap_roles` runs as a `CREATEROLE` admin that is not superuser, then it
  succeeds, and a second run changes nothing.
- Given `create_workspace_with_owner` called without a country, currency or time zone, when run, then it
  fails; given `currency='inr'` or `country_code='IND'`, then the database refuses the row.
- Given a signed-in user who is not a member of workspace B, when they request `/w/<B>/` or
  `/w/<random uuid>/`, then the response is 404 and a `workspace_access_refused` log line is written
  (NFR-001).
- Given a user with active memberships in A and B, when `workspace_ids_for_user` runs with no context,
  then it returns exactly A and B and no other column.
- Given all migrations, when CI's round trip runs, then they apply, reverse to zero and re-apply.
