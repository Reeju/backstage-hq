# T-05: Permission policy `authorize()` and the matrix file

**Tier:** A (permissions)
**Links:** PRD section 7.2 (matrix) and 5.P foundation; FR-004 AC3 (groundwork); FR-215 AC3 and
FR-268 (never-delegable list, tested now); FR-235 (assistant overlay); ADR-008; architecture
sections 10.1–10.3.
**Depends on:** T-04. Plan decision D3 approved (`edit_business_profile`; first-entry rule).

## Why
In the MVP only the owner exists, but every change must already ask one function "may this person do
this, now?" so that managers and helpers in v1 are new grants and screens, not a rebuild. The PRD's
permission matrix becomes a data file, and every row becomes a test.

## Files to touch
- `app/bhq/workspaces/policy.py`
- `app/bhq/workspaces/action_types.py`
- `app/bhq/workspaces/matrix.yaml`
- `app/bhq/workspaces/tests/test_policy.py`, `test_matrix.py`

## What to build (decisions already made)
- `action_types.py`: string constants for every action type in architecture 10.2, plus
  `edit_business_profile` (D3) and the system-only `record_security_event`. Three frozensets:
  `DELEGABLE`, `NEVER_DELEGABLE`, `OWNER_SECOND_CHECK`, copied exactly from 10.2. A unit test checks
  the three sets match 10.2 (no silent drift).
- `policy.py`:
  - `Decision` enum: `ALLOW`, `QUEUE`, `STEP_UP`, `DENY`.
  - `Actor` frozen dataclass: `kind` (`person`, `assistant`, `system`, `staff`), `user_id`,
    `on_behalf_of_user_id` (assistant only).
  - `authorize(actor, workspace_id, action_type, resource=None, context=None) -> Decision`. Pure: it
    receives the membership and grants through a small loader so it can be unit-tested without a
    database. Evaluation order, stricter wins:
    1. Unknown action type → `DENY`.
    2. `system` actor → `ALLOW` only for system action types (`record_security_event` now), else `DENY`.
    3. `assistant` actor → evaluate the person it acts for, then intersect with the 10.3 table:
       never-delegable, bank/PAN/GSTIN and its own permissions → `DENY`; anything outbound → `QUEUE`
       (never `ALLOW`); delete/disconnect/settings/export → `DENY` here (confirmation cards are a later
       feature; the person's own tap runs those Actions as a person).
    4. `person` with no active membership → `DENY`.
    5. Owner: `ALLOW`, except `OWNER_SECOND_CHECK` types → `STEP_UP` unless `context` carries a valid
       step-up proof (iteration 2) **or** `context.first_entry is True` for `change_payout_bank` /
       `change_pan_gstin` (PRD M2: first entry needs no second check) → `ALLOW`.
    6. Non-owner: `NEVER_DELEGABLE` → `DENY`; otherwise `ALLOW` only if a matching `PermissionGrant`
       exists, else `DENY`. Rule columns (amount limit, own deals, hide values, read-only, end date)
       are **not** evaluated yet: a non-owner with any rule column set gets `DENY` with reason
       `rules_not_supported_until_v1`, so nothing is ever more permissive than intended.
  - Every call returns the decision and a short machine reason (for the activity log in T-06).
- `matrix.yaml`: one entry per PRD 7.2 row: `row` (the PRD wording), `action_type`, and expected
  results per role (`owner`, `manager`, `editor`, `accountant`, `helper`, `assistant`) using the PRD
  keys (`yes`, `tick_on`, `tick_off`, `queue`, `read`, `own`, `no`, `second_check`, `as_person`,
  `tap_by_person`, `never`). Each cell also has `mvp: true|false`. Rows with no action type yet (for
  example "Use the assistant", "Global search") have `action_type: null` and are skipped with a reason.
- `test_matrix.py` parametrises over every row × role and maps cells to decisions:
  - **Run now (mvp: true):** every `owner` cell; every `assistant` cell; every cell whose row is
    never-delegable (must be `DENY` for all non-owners, including with a grant forced in).
  - **Skipped with reason "v1 rules" (mvp: false):** non-owner cells that depend on ticks or rules;
    they show in pytest output so the AC report and reviewer can see what is pending.

## Acceptance criteria
- Given the owner and any delegable action type, when `authorize` runs, then `ALLOW`.
- Given the owner and `change_payout_bank` with no step-up proof, when `authorize` runs, then
  `STEP_UP`; with `first_entry=True`, then `ALLOW`.
- Given any non-owner role, even with a grant row for it, when `authorize` runs for any never-delegable
  action type, then `DENY` (FR-268 groundwork; FR-004 AC3 groundwork for bank/PAN/GSTIN).
- Given the assistant acting for the owner, when it asks for `change_payout_bank`,
  `change_automation_settings` or `change_permissions`, then `DENY` (FR-004 AC2 and FR-215 AC3
  groundwork); when it asks for `send_invoices`, then `QUEUE`, never `ALLOW`.
- Given a person with no active membership, when `authorize` runs, then `DENY`.
- Given `matrix.yaml`, when the tests run, then every MVP cell passes and every non-MVP cell is
  reported as skipped with a reason.
