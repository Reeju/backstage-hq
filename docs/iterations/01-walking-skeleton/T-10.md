# T-10: Phone sign-up and sign-in with SMS code

**Tier:** A (authentication)
**Links:** FR-001 AC1, AC2; NFR-027 (in part: server-side sessions, 30 days of inactivity);
NFR-028 (in part: limits on codes and sign-in); NFR-032 (lockout logged); ADR-012; architecture
sections 6.2 (`AUTH_IDENTITY`, `USER_SESSION`), 9; mockup **S-01** (Phone, Code, Wrong code, Locked).
**Depends on:** T-06 (Actions and security events), T-07 (workspace key on sign-up), T-09 (redaction).

## Why
The creator's first touch. A phone number and a 6-digit text code create their account and a private
workspace with them as owner, then profile setup opens. Wrong codes are limited so nobody can guess
their way in.

## What to build (decisions already made)
**Codes (architecture 9).**
- `OneTimeCode`: `id`, `purpose` (`sign_in`; T-11 adds `verify_email`, `second_factor`), `channel`
  (`sms`, `email`), `target_hash` (HMAC-SHA256 of the normalised phone/email with `OTP_PEPPER`),
  `code_hash` (HMAC-SHA256 of code + code ID with `OTP_PEPPER`; a plain SHA of a 6-digit code is
  guessable offline), `expires_at` (+5 minutes), `consumed_at`, `attempts`. Global table (no RLS).
- Codes: 6 digits from `secrets.randbelow`; constant-time comparison; single use; a new code
  invalidates older unconsumed codes for the same target and purpose.
- **Lockout (FR-001 AC2):** `SignInThrottle` per `target_hash`: counts consecutive wrong entries across
  all codes for that target (requesting a new code does **not** reset it). On the 5th wrong entry:
  `locked_until = now + 15 minutes`; while locked, no code is sent or accepted. A correct entry resets
  the count. Logging: a technical log line `sign_in_locked` with the masked phone; and, if a user with
  that phone exists, `record_security_event` (T-06) writes "Sign-in paused for 15 minutes after 5 wrong
  codes" into each workspace they own (S-01's locked state promises "We have noted this attempt in your
  activity log").
- **Send limits (NFR-028):** per target at most 3 codes per 15 minutes; per client IP at most 10 code
  requests per hour (IP from the ALB's `X-Forwarded-For`, rightmost untrusted hop; settings
  `TRUSTED_PROXY_COUNT`). Over the limit: a plain message, no SMS sent, a warning log. Values in
  settings so they can be tuned.
- Phone numbers normalised to E.164 with `phonenumbers`, default region IN; only regions in
  `ALLOWED_PHONE_REGIONS` (default `["IN"]`) accepted, with the message "Only Indian mobile numbers can
  sign up for now."

**SMS clients.** `Msg91Client` (MSG91 OTP/flow API over `httpx`, DLT template ID and sender ID from
settings/Secrets Manager, 10-second timeout, no retry inside the request), `FakeSmsClient` (stores the
last code per number in memory for tests and Playwright), `StagingEmailRelayClient` (risk R1: emails the
code to an address in `SMS_RELAY_ALLOWLIST` mapped from the phone number; refuses numbers not mapped).
`checks.py`: system check **error** if `SMS_BACKEND` is `fake` or `email_relay` under the production
settings module. Sending happens in the request (architecture section 2 shows web → SMS); a provider
failure shows "We could not send the code. Try again in a minute." and logs the provider status only.

**Sign-up / sign-in flow (S-01).**
- `GET/POST /signin` (phone form) → issues code → `/signin/code`. The pending phone and code ID live in
  the session (pre-authentication), never in the URL.
- `POST /signin/code`: wrong → "That code is not right. You have N tries left." (N = 5 − consecutive
  wrong); locked → the S-01 locked message with the unlock time in IST.
- Correct and **no user** with that phone: one transaction creates `User` (verified `phone_e164`),
  `AuthIdentity(provider="phone", subject=<E.164>)`, then runs the Action `accounts.sign_up`
  (`creates_workspace=True`, T-06) which creates the workspace, the owner membership and the workspace
  key (T-07) and logs "You created this workspace". Then `login()` (session key cycled) and redirect to
  `/w/<id>/setup/profile` (FR-001 AC1). The route exists as a placeholder page until T-14.
- Correct and **existing user**: hand over to `accounts.signin.complete_first_factor(request, user,
  method="phone")`. In this ticket it simply logs in and redirects to the user's workspace (first ID
  from `workspace_ids_for_user`); T-11 replaces its body with the new-device check. Keep this one
  function as the only place that calls `login()`.
- `POST /signout`: deletes the session row.
- All auth views use `sensitive_post_parameters`, `never_cache`, CSRF, and `Cache-Control: no-store`.

**Sessions (NFR-027).** Custom session engine `accounts.session_store` on a model
`UserSession(AbstractBaseSession)` with `user_id` (nullable before login), `last_seen_at`,
`device_summary` ("Chrome on Android" from `user-agents`, never the raw user-agent string). Update
`last_seen_at` at most once every 5 minutes. `SESSION_COOKIE_AGE = 30 days`,
`SESSION_SAVE_EVERY_REQUEST = True` (sliding 30 days of inactivity), `SESSION_COOKIE_HTTPONLY`,
`SESSION_COOKIE_SAMESITE="Lax"`, secure in staging/production. The "Devices and sessions" card and
"Sign out everywhere" use this table in iteration 2.

## Acceptance criteria
- **FR-001 AC1 (verbatim):** Given a new person, when they sign up with their phone and the correct
  code, then a workspace is created with them as **owner** and profile setup opens.
- **FR-001 AC2 (verbatim):** Given a wrong code entered 5 times, when they try again, then sign-in is
  locked for 15 minutes and the attempt is logged.
- Given a lock, when 15 minutes pass, then a new code can be requested and used.
- Given a code older than 5 minutes, or already used, when entered, then it is refused.
- Given 4 code requests for one number within 15 minutes, when the 4th is made, then no SMS is sent.
- Given an existing user, when they sign in with a correct code, then no new workspace is created.
- Given a session unused for 30 days, when the browser makes a request, then it is signed out
  (NFR-027, in part).
- Given the database, when `OneTimeCode` and `UserSession` rows are read, then no plaintext code or
  phone number is stored in `OneTimeCode`, and no raw user-agent in `UserSession`.
- Given production settings with the fake or relay SMS backend, when `manage.py check` runs, then it fails.
