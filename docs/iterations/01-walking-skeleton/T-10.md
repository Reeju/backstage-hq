# T-10: Email-code sign-up and sign-in, with the workspace country

(Revised for CR-001, 2026-11-11.) Was "Phone sign-up and sign-in with SMS code". Changes: email
replaces phone as the first factor and the sign-in identity; a country choice creates the workspace's
country, currency and time zone; the SMS part shrinks to an interface and a fake client behind a
per-country switch that is off; the email-code job moves here from T-11; lock-out times are shown in
the workspace's time zone. The invite-only check and the waitlist are T-18.

**Tier:** A (authentication)
**Links:** FR-001 AC1, AC2, AC3; FR-005 AC1 (country at sign-up); NFR-027 (in part: server-side
sessions, 30 days of inactivity); NFR-028 (in part: limits on codes and sign-in); NFR-032 (lock-out
logged); ADR-012 (as amended, C4); ADR-014 (as amended, C3); architecture sections 6.2 (`USER`,
`AUTH_IDENTITY`, `USER_SESSION`, `WORKSPACE`), 9; mockup **S-01** as amended for CR-001 (email field,
country choice, Code, Wrong code, Locked).
**Depends on:** T-06 (Actions and security events), T-07 (workspace key on sign-up), T-08 (the email
job), T-09 (redaction), T-13 (the rules registry: `supported_countries()` and the country's currency
and time zone). **Gate:** the S-01 mockup amendment approved by the owner (GQ10); if it is late, build
the logic and tests first and the template last.

## Why
The creator's first touch, in any country, at near-zero cost. An email address and a 6-digit emailed
code create their account and a private workspace for the country they chose, with them as owner; then
profile setup opens. Wrong codes are limited so nobody can guess their way in.

## What to build (decisions already made)
**Codes (architecture 9).**
- `OneTimeCode`: `id`, `purpose` (`sign_in` now; T-11's factors are not codes we send),
  `channel` (`email`, `sms`), `target_hash` (HMAC-SHA256 of the normalised email with `OTP_PEPPER`),
  `code_hash` (HMAC-SHA256 of code + code ID with `OTP_PEPPER`), `expires_at` (+5 minutes),
  `consumed_at`, `attempts`. Global table (no RLS).
- 6 digits from `secrets.randbelow`; constant-time comparison; single use; a new code invalidates older
  unconsumed codes for the same target and purpose.
- Email normalisation: strip, lower-case the whole address, validate with `email-validator` (syntax
  only, no DNS lookup in the request). One function, `accounts.identity.normalise_email`, used
  everywhere (T-18 and T-11 reuse it).
- **Lock-out (FR-001 AC2):** `SignInThrottle` per `target_hash` counts consecutive wrong entries across
  all codes for that target (a new code does **not** reset it). On the 5th wrong entry,
  `locked_until = now + 15 minutes`; while locked no code is sent or accepted. A correct entry resets
  the count. Logging: technical log line `sign_in_locked` with the masked email; and, if a user with
  that email exists, `record_security_event` (T-06) writes "Sign-in paused for 15 minutes after 5 wrong
  codes" into each workspace they own. The locked page shows the unlock time in the **workspace's time
  zone** if the user exists, otherwise in the time zone of the country chosen on the form (FR-005 rule
  4); never a hard-coded "IST". T-11 counts wrong authenticator and backup codes into the same throttle.
- **Send limits (NFR-028, app part):** per email at most 3 codes per 15 minutes; per client IP at most 10
  code requests per hour. Client IP comes from `CLIENT_IP_HEADER` (staging value recorded by spike
  Q-H1) or the rightmost untrusted hop of `X-Forwarded-For` with `TRUSTED_PROXY_COUNT`. Over the limit:
  a plain message, no email sent, a warning log. Values in settings.

**Email code job.** `POST /signin` creates an `EmailCodeRequest` row (`purpose`, `email`, `created_at`;
global, deleted once sent) and defers `accounts.send_email_code` with the request ID only (queue
`realtime`, not workspace-scoped). The job generates the code, stores only its HMAC in `OneTimeCode`,
sends the email, and deletes the request row. **The code and the address are never job arguments.**
Email: subject "Your BackstageHQ code", the code, its 5-minute expiry, "If this wasn't you, you can
ignore this email." From `no-reply@<domain>`. The page says "Code sent" at once.

**SMS behind a switch (FR-001 AC3).** `sms.py` holds only the `SmsClient` protocol
(`send_code(e164, code) -> None`) and `FakeSmsClient` (stores the last code per number in memory, for
tests). `PHONE_SIGNIN_COUNTRIES` (default `[]`) decides, per country, whether a phone option is shown;
with the default, no phone field or link is rendered anywhere. No real SMS client, no relay, no
`phonenumbers` dependency in this ticket.

**Sign-up and sign-in flow (amended S-01).**
- `GET/POST /signin`: one form with **email** and **"Where is your business based?"**: the list from
  `bhq.rules.registry.supported_countries()` (India only) plus "My country is not listed". The browser
  suggestion (`Accept-Language` region) pre-selects a supported country but the person must submit the
  form to confirm it; nothing is assumed silently. "My country is not listed" goes to T-18's waitlist
  page and sends no code. The pending email, the chosen country and the code request ID live in the
  pre-authentication session, never in the URL. The country is ignored for an existing user.
- `POST /signin/code`: wrong → "That code is not right. You have N tries left." (N = 5 − consecutive
  wrong); locked → the S-01 locked message.
- Correct and **no user** with that email: one transaction creates `User` (verified `email`),
  `AuthIdentity(provider="email", subject=<normalised email>)`, then runs the Action `accounts.sign_up`
  (`creates_workspace=True`, T-06) with the chosen `country_code`, which reads the rule set's
  `currency` and `timezone` and calls `create_workspace_with_owner(user, country_code=..., currency=...,
  timezone=...)` (T-04), creates the workspace key (T-07) and logs "You created this workspace". Then
  `complete_first_factor` logs in (session key cycled) and redirects to `/w/<id>/setup/profile`
  (FR-001 AC1, FR-005 AC1). The route exists as a placeholder until T-14.
- Correct and **existing user**: `accounts.signin.complete_first_factor(request, user,
  method="email")`. In this ticket it logs in and redirects to the user's workspace (first ID from
  `workspace_ids_for_user`); T-11 replaces its body with the new-device check. This stays the only
  place that calls `login()`.
- `POST /signout`: deletes the session row.
- All auth views use `sensitive_post_parameters`, `never_cache`, CSRF, and `Cache-Control: no-store`.
- T-18 adds the invite-only check in front of "create `EmailCodeRequest`"; leave one function,
  `accounts.signin.may_request_code(email) -> bool`, returning `True` here, as the hook.

**Sessions (NFR-027).** Custom session engine on `UserSession(AbstractBaseSession)` with `user_id`
(nullable before login), `last_seen_at`, `device_summary` ("Chrome on Android" from `user-agents`,
never the raw user-agent string). Update `last_seen_at` at most once every 5 minutes.
`SESSION_COOKIE_AGE = 30 days`, `SESSION_SAVE_EVERY_REQUEST = True`, `HttpOnly`, `SameSite=Lax`, secure
in staging and production.

**Production checks (`checks.py`).** A Django system check **error** under the staging or production
settings module if `EMAIL_BACKEND` is the locmem, console, file or SMTP-to-Mailpit backend, or if
`PHONE_SIGNIN_COUNTRIES` is not empty while the SMS client is the fake one.

## Acceptance criteria
- **FR-001 AC1 (verbatim):** Given a new invited person in a supported country, when they sign up with
  their email and the correct code, then a workspace is created with them as **owner** and profile
  setup opens. (Invite check: T-18; here every address may request a code.)
- **FR-001 AC2 (verbatim):** Given a wrong code entered 5 times, when they try again, then sign-in is
  locked for 15 minutes and the attempt is logged.
- **FR-001 AC3 (verbatim):** Given phone sign-in is off for a country, when the sign-in screen opens,
  then no phone option is shown.
- **FR-005 AC1 (verbatim):** Given a person signing up, when they choose India, then the workspace is
  created with country India, currency INR, time zone Asia/Kolkata and the current Indian rule set.
- Given a lock, when 15 minutes pass, then a new code can be requested and used.
- Given a code older than 5 minutes, or already used, when entered, then it is refused.
- Given 4 code requests for one email within 15 minutes, when the 4th is made, then no email is sent.
- Given an existing user, when they sign in with a correct code, then no new workspace is created and
  the country on the form is ignored.
- Given the email job, when inspected, then its arguments hold no code and no email address, and it
  sends exactly once.
- Given a session unused for 30 days, when the browser makes a request, then it is signed out.
- Given the database, when `OneTimeCode` and `UserSession` rows are read, then no plaintext code or
  email is stored in `OneTimeCode`, and no raw user-agent in `UserSession`.
- Given staging or production settings with a test email backend, or a phone country switched on with
  the fake SMS client, when `manage.py check` runs, then it fails.
