# T-11: Authenticator app and backup codes as the second method, and the new-device check

(Revised for CR-001, 2026-11-11.) Was "Second sign-in method (verified email) and new-device check".
Changes: the second method is an authenticator app (TOTP) with 10 backup codes, not a verified email;
setup works on a single phone ("Open in authenticator app", "Copy setup key"); the new-device check
offers the authenticator or a backup code, never an email code; the email-code job moved to T-10; the
"email already used" rule moved to T-10 (email is now the sign-in identity).

**Tier:** A (authentication)
**Links:** FR-002 AC1, AC2, AC3, AC4, AC5 (PRD "Always a second method", GL13); NFR-004; NFR-032
(new-device sign-in logged); ADR-012 (as amended, C4); ADR-005 (platform key, C7); architecture
sections 6.2 (`TOTP_DEVICE`, `BACKUP_CODE`, `TRUSTED_DEVICE`), 9, 12; mockups **S-01** (New-device
state, as amended) and **S-02** (authenticator card, as amended).
**Depends on:** T-10 (`complete_first_factor`, the throttle), T-07 (platform key for the seed).

## Why
An email code alone is only as safe as the creator's mailbox. So every creator sets up a second method
of a different kind, an authenticator app that works offline in every country at no cost, and any new
phone or browser must pass it before seeing any data. Backup codes stop a lost phone from locking them
out.

## What to build (decisions already made)
**Authenticator setup (FR-002 AC3).**
- `POST /account/second-method/authenticator/start` (signed in, no confirmed device): create or replace
  an unconfirmed `TotpDevice` with a fresh 160-bit base32 seed, encrypted with
  `crypto.encrypt_user_field(user_id, "accounts_totpdevice", "secret_enc", seed)` (T-07). Render the
  card with: a QR code of the `otpauth://totp/BackstageHQ:<masked email>?secret=...&issuer=BackstageHQ`
  URI as inline SVG (`segno`), an **"Open in authenticator app"** link to the same URI (works on a phone
  that has an authenticator installed), and **"Copy setup key"** showing the seed in groups of 4 with a
  copy button. The seed is never logged and never put in a URL other than the `otpauth://` link.
- `POST /account/second-method/authenticator/confirm` with a 6-digit code: verify with `pyotp` (30-second
  step, `valid_window=1`); on success set `confirmed_at` and `last_used_step`, generate the backup codes
  (below) and show them once with "I have saved these codes" (required tick). Log "You set up an
  authenticator app" via `record_security_event`, and mark **this device** trusted (both factors were
  just shown here).
- Replay protection: a code whose time step is less than or equal to `last_used_step` is refused.
- Wrong codes count toward T-10's `SignInThrottle` for the user's email target (the same 5-try,
  15-minute lock).

**Backup codes (FR-002 AC5).** 10 codes, each 10 characters from a 32-letter alphabet without look-alikes
(shown as `xxxxx-xxxxx`), stored only as HMAC-SHA256 with `OTP_PEPPER` in `BackupCode`; shown once.
Verifying normalises case and dashes, compares in constant time, and sets `used_at`; a used code is
refused. Regenerating (iteration 2 settings card) replaces the whole batch.

**`SecondMethodRequiredMiddleware`.** A signed-in user with no confirmed authenticator (and no verified
phone where phone codes are on) who requests any `/w/...` page other than `/w/<id>/setup/profile` and the
second-method endpoints is redirected to `/w/<id>/setup/profile`. Setup cannot finish without it
(PRD M1: "This step cannot be skipped").

**New-device check (FR-002 AC1, AC2, AC4).**
- Trusted-device cookie `bhq_device`: 32 random bytes, URL-safe base64, `Secure` (staging and
  production), `HttpOnly`, `SameSite=Lax`, max-age 400 days. `TrustedDevice` stores `SHA-256(cookie)`,
  `user_id`, `last_sign_in_at`, `created_at`.
- `complete_first_factor(request, user, method)` (the single `login()` site from T-10):
  - Cookie matches a `TrustedDevice` of this user with `last_sign_in_at` within 30 days → log in, update
    `last_sign_in_at`, go to the workspace (AC2).
  - Otherwise do **not** log in. Store `pending_user_id`, `first_method` and an expiry (10 minutes) in
    the session and redirect to `/signin/check`. No `/w/...` page is reachable in this state (AC1).
  - The check offers **the authenticator code** and **"Use a backup code"**, and (only where phone codes
    are switched on and the user has a verified phone) a phone code. It never offers an email code or
    Google when the first factor was email (AC4). A user with no confirmed second method (only possible
    if they abandoned setup) sees "Finish setting up on the device you signed up on, or contact
    support" and is not logged in.
  - On a correct code: `login()`, cycle the session key, and if "Remember this device for 30 days" is
    ticked (unticked by default), create or refresh `TrustedDevice` and set the cookie. Log "New
    sign-in on <device summary>" via `record_security_event` (NFR-032). A backup-code sign-in also logs
    "A backup code was used (N left)".
  - Wrong codes count toward the same throttle.

## Acceptance criteria
- **FR-002 AC1 (verbatim):** Given a creator signs in on a new device, when the first step succeeds, then
  the app asks for a second factor before showing any data.
- **FR-002 AC2 (verbatim):** Given a known device, when the creator signs in within 30 days of their last
  sign-in on it, then no second factor is asked.
- **FR-002 AC3 (verbatim):** Given a creator who signed up with an email code or Google, when profile
  setup finishes, then an authenticator app (or a verified phone where switched on) is on the account
  and backup codes were shown once.
- **FR-002 AC4 (verbatim):** Given a new-device sign-in with an email code or Google, when the second
  factor is asked, then the choices are the authenticator code, a backup code or (where switched on) a
  phone code, never an email code or Google for the same address.
- **FR-002 AC5 (verbatim):** Given a backup code already used, when entered again, then it is refused.
- Given a known device last used 31 days ago, when the creator signs in, then a second factor is asked.
- Given a signed-in creator with no confirmed authenticator, when they open Home, then they are sent to
  profile setup.
- Given an authenticator code already accepted, when the same code is entered again in the same time
  step, then it is refused.
- Given the database, when `TotpDevice` and `BackupCode` rows are read with raw SQL, then no seed and no
  backup code appears in plaintext, and neither appears in any log line or Sentry event.
- Given 5 wrong authenticator or backup codes for one account, when a 6th is tried, then sign-in is
  locked for 15 minutes (shared throttle).

  a second method (only when a country is switched on); the S-02 page itself (T-14).
