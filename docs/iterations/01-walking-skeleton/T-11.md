# T-11: Second sign-in method (verified email) and new-device check

**Tier:** A (authentication)
**Links:** FR-002 AC1, AC2, AC3, AC4 (PRD M1 "Always a second method"); NFR-004; NFR-032 (new-device
sign-in logged); ADR-012; architecture sections 6.2 (`TRUSTED_DEVICE`), 9; mockup **S-01** (New-device
state), **S-02** (the second-method card is added by PRD M1; the mockup predates it).
**Depends on:** T-10, T-08 (email codes are sent by a job).

## Why
A text-message code alone can be stolen (SIM swap). So every creator must have a second way to sign
in of a different kind, and any new phone or browser must pass it before seeing any data.

## What to build (decisions already made)
**Second method (FR-002 AC3, M1).**
- For a signed-in user without a verified email: `POST /account/second-method/email` with an address →
  normalise (lower-case, strip), refuse if another user already has it verified (message: "This email is
  already used by another account."), create an `EmailCodeRequest` row (`user_id`, `purpose`,
  `email`, `created_at`; global table, deleted once sent) and `defer` `accounts.send_email_code` with the
  request ID only (queue `realtime`, not workspace-scoped). The job generates the code itself, stores
  only its HMAC in `OneTimeCode`, sends the email, and deletes the request row. **The code and the
  address are never job arguments.** The page says "Code sent" at once; the job normally runs within
  seconds.
- `POST /account/second-method/email/verify` with the code → sets `user.email`, adds
  `AuthIdentity(provider="email")`, logs "You verified a second sign-in method" via
  `record_security_event`, and marks **this device** trusted (both factors have now been shown here).
- The same 5-wrong-codes lock as T-10 applies, per email target.
- `SecondMethodRequiredMiddleware`: a signed-in user with no verified second method who requests any
  `/w/...` page other than `/w/<id>/setup/profile` and the second-method endpoints is redirected to
  `/w/<id>/setup/profile`. So setup cannot finish without it (M1: "This step cannot be skipped").
- The partial `_second_method_card.html` holds the email field, "Send code", the code field and the
  "Verified" chip, with HTMX swaps; T-14 places it on S-02.

**New-device check (FR-002 AC1, AC2, AC4).**
- Trusted-device cookie `bhq_device`: 32 random bytes, URL-safe base64, `Secure` (staging/production),
  `HttpOnly`, `SameSite=Lax`, max-age 400 days. `TrustedDevice` stores `SHA-256(cookie)`, `user_id`,
  `last_sign_in_at`, `created_at`.
- `complete_first_factor(request, user, method)` (the single `login()` site from T-10):
  - If the cookie matches a `TrustedDevice` of this user with `last_sign_in_at` within 30 days → log in,
    update `last_sign_in_at`, go to the workspace (AC2).
  - Otherwise do **not** log in. Store `pending_user_id`, `first_method`, and an expiry (10 minutes) in
    the session and redirect to `/signin/check`. No `/w/...` page is reachable in this state (AC1).
  - The second factor must be of a different kind from `first_method`: after `phone` only `email` is
    offered (AC4: never a second phone code). If the user has no verified email (only possible for a
    user who abandoned setup), show "Finish setting up on the device you signed up on, or contact
    support" and do not log in.
  - On a correct second-factor code: `login()`, cycle the session key, and if "Remember this device for
    30 days" is ticked (unticked by default), create or refresh `TrustedDevice` and set the cookie.
    Log "New sign-in on <device summary>" via `record_security_event` (NFR-032).
  - Wrong second-factor codes count toward the same 5-try lock for that email target.
- The second-factor email code uses the same job, with an `EmailCodeRequest` for `user.email`.
- Email for codes: subject "Your BackstageHQ code", body with the code, its 5-minute expiry and "If
  this wasn't you, you can ignore this email." Sent from `no-reply@<domain>` via SES (staging) or
  Mailpit (local).

## Acceptance criteria
- **FR-002 AC1 (verbatim):** Given a creator signs in on a new device, when the first step succeeds,
  then the app asks for a second factor before showing any data.
- **FR-002 AC2 (verbatim):** Given a known device, when the creator signs in within 30 days of their last
  sign-in on it, then no second factor is asked.
- **FR-002 AC3 (verbatim):** Given a creator who signed up with a phone code, when profile setup
  finishes, then a verified email address or a linked Google account is on the account.
- **FR-002 AC4 (verbatim):** Given that creator signs in on a new device with a phone code, when the
  second factor is asked, then the choices are an email code or Google, never a second phone code.
  (In this iteration the only choice is the email code; Google is added in iteration 2.)
- Given a known device last used 31 days ago, when the creator signs in, then a second factor is asked.
- Given a signed-in creator with no verified email, when they open Home, then they are sent to profile
  setup.
- Given an email already verified by another user, when entered as a second method, then it is refused.
- Given the email job, when inspected, then its arguments hold no code and no email address.
